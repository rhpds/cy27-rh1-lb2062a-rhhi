= Multi-Stage Builds and Operating Hardened Images

Our application works fine, but we're carrying packages we don't explicitly need.
What we need is a way to separate the run time and build time dependencies. 
In Python, this may not be as critical as other languages, but we can still look at a pattern that makes that separation possible.

== The Multi-Stage Solution

Multi-stage builds divide the work into blocks of base images and instructions, in the same fashion as the all-in-one approach we've used this far.

Stage one uses the builder variant to install Flask into a target directory.
The standard RUN command works as expected since the `builder` includes a shell.
Stage two copies only that directory into the lean default runtime — the builder and its packages are discarded.

These may look like you took 2 different Containerfiles and used `cat` to combine them.
Each stage is defined by a new `FROM` line, we'll see how that works in practice on our new `Containerfile.hardened` example.

TIP: This is an extremely simple example for the purposes of this lab, production multi-stage builds can be much more complicated to increase isolation between build and runtime dependencies, including full compile chains that only copy final binaries.

[source,bash,role=execute]
----
cat ~/flask/Containerfile.hardened
----

[source,dockerfile]
----
include::example$flask/Containerfile.hardened[]
----
<.> Stages create intermediate images
<.> final stage doesn't get an AS, will use the tag from build command
<.> --from uses the name provided in the FROM AS combination

[source,bash,role=execute]
----
podman build -t rhhi-demo:hardened -f ~/flask/Containerfile.hardened ~/flask
----
Building this image, you'll see that `podman` creates a new image for each set of steps, delimited by the new `FROM` directive.
The `AS` in that directive lets us refer to those images in later stages.
The build output will have a new `[X/Y]` label for each step to show which stage of how many the step is in. 
This makes finding issues in longer Containerfiles with many stages easier.

....
[2/2] STEP 1/9: FROM registry.access.redhat.com/hi/python:3.14
....

== Compare all our images

[source,bash,role=execute]
----
podman images rhhi-demo
----

.*Expected output:*
----
REPOSITORY           TAG         IMAGE ID      CREATED         SIZE
localhost/rhhi-demo  hardened    fbd531176581  57 seconds ago  120 MB
localhost/rhhi-demo  builder     1d8177f35b89  22 minutes ago  195 MB
localhost/rhhi-demo  ubi         5b0d4e2582f9  33 minutes ago  263 MB
----

The multi-stage final output is the smallest yet.
Let's look at the RPM counts.
Our demo images set an application entrypoint, so we have to pass `--entrypoint` to run `rpm` directly instead.

[source,bash,role=execute]
----
podman run --rm --entrypoint rpm rhhi-demo:ubi -qa | wc -l
podman run --rm --entrypoint rpm rhhi-demo:builder -qa | wc -l
podman run --rm --entrypoint rpm rhhi-demo:hardened -qa
----

.*Expected output (partial):*
----
Error: crun: executable file `rpm` not found in $PATH: No such file or directory: OCI runtime attempted to invoke a command that was not found
----

The multi-stage image has no `rpm` and no shell — both are absent by design since we deployed into the `default` runtime.
This is what distroless means in practice: the binary simply does not exist in the image.

== Looking Inside a Running Distroless Container

If a container misbehaves in production and it has no shell, no `rpm`, and no tools,
how do you inspect it *without* rebuilding it to add those tools back?

The answer is an ephemeral _debug sidecar_: a separate, disposable container that brings its own tools, but shares the target's process and network namespaces at run time.

This second container can answer what is installed in our multi-stage image. 

[source,bash,role=execute,subs=attributes+]
----
podman run --rm \
  --pid container:rhhi-hardened \
  --network container:rhhi-hardened \
  --security-opt label=disable \
  --user 0 \
  {rhhi-registry}/core-runtime:latest-builder \
  rpm --root=/proc/1/root -qa | wc -l
----

Remember, new containers get their own filesystem, networking, and isolated process tree by default.
We need to pass some specific options to make the sidecar "attach" to the container we want to examine.

`--pid container:rhhi-hardened`:: Join the *target's* process namespace instead of creating one
`--network container:rhhi-hardened`:: Reuse the *target's* network namespace 
`--security-opt label=disable`:: Drop SELinux separation so the sidecar is allowed to read the target's `/proc` entries and files
`--user 0`:: Run as root *inside the sidecar* for full read access to the target 

The `rpm` command also needs to read the target's `rpmdb`, which is a little harder in a container.
We can take advantage of the `/proc` filesystem which holds a special pointer to the filesystem of a process. 
We'll talk more about this later.

`rpm --root=/proc/1/root`:: Point `rpm` at the *target's* filesystem (reached through `/proc`), not the sidecar's own.

.*Expected output (the exact count varies by image build):*
----
99
----

The tool missing in the original image runs from the sidecar, but against the application's own files.

=== Build a Debug Sidecar

Our one-shot sidecar was useful because `rpm` just happened to already be installed. For a real debugging tool, we'll need to add our tools. 
Red Hat Hardened Images ships a set of images targeting dynamically compiled applications, which we will use here as a baseline for our debugger example.
The `busybox` package is shipped as part of the packages, which will provide us with alternatives to common Linux tools.

This makes for a very simple Containerfile, note we're explicitly calling `bash` on start.
[source,bash,role=execute,subs=attributes+]
----
cat > ~/flask/Containerfile.debug << 'EOF'
FROM {rhhi-registry}/core-runtime:latest-builder
USER root
RUN dnf -y install busybox && dnf clean all
USER 65532
CMD ["/bin/bash"]
EOF
----
This builder base image already provides `rpm`, `bash`, `curl`, and coreutils; `busybox` adds the process and network inspection applets in a single package.

Go ahead and build this new interactive sidecar.

[source,bash,role=execute]
----
podman build -t rhhi-debug -f ~/flask/Containerfile.debug ~/flask
----

The application image from earlier is still running as `rhhi-hardened`. 
Attach this interactive sidecar to it — the same namespace-sharing flags as the one-shot above, now with `bash` as the command.
This will open an interactive shell that lets us explore our running target container.

[source,bash,role=execute]
----
podman run --rm -it \
  --pid container:rhhi-hardened \
  --network container:rhhi-hardened \
  --security-opt label=disable \
  --user 0 \
  rhhi-debug bash
----
....
bash-5.3# 
....

=== Reaching the App's Files

The natural first move is to list the application directory:

[source,bash,role=execute]
----
ls /app
----

.*Expected output:*
----
ls: cannot access '/app': No such file or directory
----

The sidecar shares the target's _process_ and _network_ namespaces, but each
container keeps its own _filesystem_. `/app` lives in the target, not here.
So how did we get the `rpmdb` in our one-shot?

The kernel exposes every process's root filesystem at `/proc/<pid>/root`. 
Because we share the PID namespace, the application is PID 1 — so `/proc/1/root` is the target's entire filesystem.

[source,bash,role=execute]
----
ls -l /proc/1/root/app
----

.*Expected output:*
----
-rw-r--r--. 1 65532 65532 2224 ... app.py
----

Notice the user and group is the default non-root `65532` user.
To confirm this is the real filesystem and not just an entry showing that a file exists somewhere, check the contents of the `app.py` file.

[source,bash,role=execute]
----
head /proc/1/root/app/app.py
----

.*Expected output (partial):*
----
import os
from flask import Flask, request, render_template_string
import hashlib
----

That's the actual source of our application in its container.

=== Inspecting the Running Process

We added `busybox` to give us access to more tools without having to add a lot of extra packages to our sidecar.
Because `busybox` applets may not be symlinked onto the `PATH`, first list what is available:

[source,bash,role=execute]
----
busybox --list | pr -t -5
----

Every name in that list is an applet you invoke as `busybox <name>`. 

You can use these like you would the standard Linux command it replaces.

[source,bash,role=execute]
----
busybox ps
----

.*Expected output (partial):*
----
PID   USER     TIME  COMMAND
    1 root      0:00 python3 app.py
    4 root      0:00 bash
   13 root      0:00 busybox ps
----

The application is PID 1 in the shared process namespace.
It was run directly via the `CMD` when started, and as the sidecar _joins_ the existing namespace, the application stays as PID 1.
You can also see the `bash` shell running in the sidecar as PID 2 instead of its own PID 1 like you normally would expect.

What about open ports?
We should see the application listening somewhere, and we can also get the PID associated.

[source,bash,role=execute]
----
busybox netstat -tlnp
----

.*Expected output:*
----
Active Internet connections (only servers)
Proto Recv-Q Send-Q Local Address      Foreign Address     State       PID/Program name 
tcp        0      0 0.0.0.0:8080       0.0.0.0:*           LISTEN      1/python3
----

The socket belongs to PID 1, and the bound address is `INADDR_ANY` - all IPv4 addresses on the local host.

Finally, check the app over the shared network namespace:

[source,bash,role=execute]
----
curl -s -o /dev/null -w "HTTP %{http_code}\n" localhost:8080/crypto-demo
----

.*Expected output:*
----
HTTP 200
----

`localhost` inside the sidecar is the same as the application's `localhost`, since they share the namespace.

Exit the sidecar and the application container is still running, no new application debug image or tools copied into it.

[source,bash,role=execute]
----
exit
----

[source,bash,role=execute]
----
podman ps
----

[NOTE]
====
For production debugging, `procps-ng`, `iproute`, and `gdb` are available in the
hummingbird repositories and can be added to the debug image the same way. The
principle holds either way: debug tools live in a disposable sidecar, never in the
shipped image.
====

[source,bash,role=execute]
----
podman stop rhhi-hardened
----

The multi-stage runtime carries only what the interpreter needs at runtime.
Build tools are in stage one and never committed to the final image.
Ephemeral sidecars can provide debugging and troubleshooting without the need for complex builds or substituting images.
